# このプロジェクトについて

## 作った人

高校 2 年のとき、スマホの LINE から家のエアコンやテレビを動かしてみたくて、Raspberry Pi でプログラミングを始めました。

2023 年から 2026 年 7 月まで、製造業の工場で働いていました。設備保全から始まり、自分で作った異常検知がきっかけで DX の部署に約 1 年いたあと、ICTグループと、担当課の前工程 8 ラインの保全を兼務していました。入社 2 年目からは副業で IT スタートアップに入り、GitHub や TypeScript・Next.js、チームでの開発を一から教わりました。

## 作ったきっかけ

当時の記録システムは VB.NET で、控室の PC でしか開けませんでした。開くまでに時間がかかり、動きも遅く、探し方は「工場 → ライン → 設備」とたどるだけです。故障の内容の言葉では探せず、調べものに 30 分近くかかっていた感覚があります。

困っていたのは、たとえばこんなところです。

| 誰が | 困っていたこと |
|---|---|
| 3 交代の保全班 | 全ラインを横断して受け持つので、癖のある設備や最近の故障の傾向まで把握しきれない |
| 若手 | 初めての故障に苦戦する。先輩の付き添いなしで対応することも少なくない（自分の悩みでもありました） |
| 記録 | 毎回くわしく書いているのに、故障が起きたときに探せず、活かされていない |

設備が 120 分を超えて止まると「重大故障」になり、生産に響くうえ、なぜなぜ分析や再発防止にも多くの時間を取られます。

> 夜間に故障 → 3 交代班が原因をつかめず 120 分を超える → 翌日に調べたら、同じ現象が過去に何度も起きていて、記録どおりにやれば 5 分で直せた

過去の記録をすぐに探せれば防げたはずだ、と思ったのがきっかけです。

もう一つ、副業で RAG（検索と AI の回答を組み合わせるしくみ）の案件に触れていて、LangChain というライブラリの中で何が起きているのかを、自分で組んで理解したいという気持ちもありました。

## 開発の流れ

仕事のあとの時間に、会社の PC で作りました。公開しているこのリポジトリは、自分の PC で作り直したデモです。会社の保全記録は入っていません。

1. **試作**：Python と Streamlit で、ベクトル検索だけの小さなものを作りました。専門用語（「チャッキングミス」「リミットスイッチ」）やエラーコードの完全一致に弱いことが分かりました
2. **検索の組み合わせ**：キーワード検索（BM25）を足して順位を合わせ、最後に並べ直すようにしました
3. **作り直し**：試作で使っていた FAISS と LangChain をやめ、PostgreSQL + pgvector と自分で書いた検索の流れに置き換えました。再起動のたびに索引を作り直す手間をなくし、中のしくみも自分で説明できるようにするためです
4. **Web アプリ化**：副業で覚えた Next.js と、FastAPI で Web アプリにしました。スマホの画面でも使えます
5. **評価して直す**：評価の仕組みを作って最初の状態を測り、索引の方式・質問の表記・略語・語の形と、1 つずつ直しました

記録は社外のサービスに送れないため、検索に使うモデルはすべて手元で動かしています。AI モードを社内の生成 AI（ChatAGC）につなぐ許可は、情報システム部門にもらいました。公開しているデモ版は、代わりに OpenAI の API を使っています。

AssistChat が一通り動くころ、ICTグループでも RAG を作ることになりました。全工場のデータを Databricks にそろえる、会社の正式なプロジェクトです。現場で使われるのはそちらで、AssistChat 自体は続けていません。ICTグループの上長が、個人で RAG を作っていることを知っていて、声をかけてくれました。ICTグループのメンバーとして、要件定義から実装まで担当しました。生成 AI は、こちらでも ChatAGC を使いました。

## 苦労したこと

**「動くけど、中が分からない」**

最初は LangChain で動かせましたが、なぜその記録が出てくるのかを説明できませんでした。ベクトル検索・キーワード検索・並べ直しを一つずつ自分で書き直して、ようやく説明できるようになりました。

**「良くなったのかが分からない」**

正解データが無いので、直しても良くなったのか判断できませんでした。質問と正解を自分で作り、直すたびに同じ物差しで測るようにしました。索引の探し方を変えたときには、公開デモで、症状文を質問にしたベクトル検索の Hit@5（上位 5 件に正解が入る割合）が 0.62 から 0.77 に上がりました。会社の保全記録では、採用した方式のこの割合が 0.72 です。詳しくは [評価のまとめ](EVALUATION.md) に書きました。AI モードの回答の質は、まだ測れていません。

**「AI が書いたコードを、どう確かめるか」**

コードの多くは AI（Claude、Cursor）を使って書きました。任せきりにしないために、直す内容を小さく区切り、「直す前の記録 → 直す → 直した後の記録 → 比べる」を毎回やるようにしました。同じ検索を同時に投げると結果が食い違う不具合も、この確認の中で見つけて直しました。最後の通しの確認では、「AI に質問」のボタンを押しても AI モードに切り替わらない不具合が見つかりました。これも、先にテストで再現してから直しています。

## 学んだこと

- **測ってから直す**：感覚で直すと、良くなったのかが分かりません。先に物差しを作るのが近道でした
- **現場の言葉で考える**：保全員が実際にどう入力するかを想像して、質問や表記の揺れを考えました。現場にいたことが一番活きたところです
- **AI を使っても、確かめるのは自分**：AI のおかげで作れる範囲は広がりましたが、正しく動いているかを確かめる手順は自分で持つ必要がありました

分からないことは、記事や本、IT の展示会で調べながら進めました。まだ知らないことも多いので、これからも現場の困りごとを IT で解決する仕事を通して身につけていきたいです。
