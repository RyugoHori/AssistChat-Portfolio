# 評価のまとめ

会社の保全記録で検索のやり方を選び、公開デモで同じ手順を再現できるようにしました。会社の記録そのものは社外に出せないので、このリポジトリのスクリプトが測るのは公開デモです。スクリプトは `tools/evaluation`、公開デモの結果は `tools/evaluation/results` にあります。

## なぜ評価の仕組みから作ったか

- 正解データ（質問と、その答えになる記録の組）は、最初からありませんでした
- 実際に使う保全員に、評価のために時間をもらうのは難しい状況でした
- 保全記録は、外部のサービスに送れません

そこで、自分が保全員として現場の聞き方や故障を知っていることを活かして、少ない手間で方式を選び、直して良くなったかを確かめる数字が出る形にしました。

## 見ている数字

画面には 10 件出しますが、現場の人が目を通すのは上の数件なので、すべて上位 5 件で見ています。

| 数字 | 意味 |
|---|---|
| Hit@5 | 上位 5 件に正解が 1 件でも入った質問の割合 |
| MRR@5 | 最初の正解が何位に出たか（1 位なら 1、2 位なら 0.5、5 位までに無ければ 0）を、質問全体で平均した値 |
| 質問ごとの勝ち負け | 2 つの方式で、最初の正解の順位がどちらが上だったか |
| 応答時間 | 1 回の検索にかかった時間の中央値 |

- 同じ記録が分割されて何度か出た場合は、1 件として数えます

## 比べた方式

| 方式 | 内容 |
|---|---|
| dense | ベクトル検索だけ。質問と記録の意味の近さで探す |
| sparse | キーワード検索だけ。BM25 は、単語の出現で点数をつける |
| hybrid | 2 つの上位 10 件を RRF（k=60）で合わせる。式は設計のまとめに書きました |
| hybrid_rerank | hybrid の上位 10 件を Cross-Encoder で並べ直す（採用した設定） |

## 測り方

2 種類あります。手で書いた質問が評価A、過去の記録の症状文をそのまま質問にしたものが評価Bです。方式を選んだのは評価Aです。評価Bは補助です。

質問を書いたのも、正解を付けたのも、測ったのも自分です。在職中（2026 年 7 月まで）に測りました。

### 評価A：手で書いた質問

- 現場の人が入れそうな質問を、自分で書きました。会社の保全記録は 52 問で、正解が無かった 8 問を除いた 44 問で集計しています。公開デモは 40 問で、同じく正解が無かった 2 問を除いた 38 問です
- 質問は検索結果を見る前に書き、結果を見てから差し替えていません
- 正解はプーリングで付けました。質問ごとに、ベクトル検索（全件を正確に比べるもの）とキーワード検索の上位 10 件を集め、並びをシャッフルして、どの方式の結果か分からない状態で判定します
- 「同じ原因・同じ処置で、そのまま対応の参考になる記録」を正解にしました。AI に下書きの判定をさせ、全件を自分で確認して決めています

### 評価B：症状文を質問にする

- 記録の「症状」の文を、質問として使います
- 探す対象は、その記録より前の日付の記録だけです
- 「同じ設備の種類（equipment2）で、同じ原因分類」の過去の記録を正解にしました
- 症状の文は記録の書き方そのままなので、キーワード検索が有利になりやすいです

## 会社の保全記録

評価A（44 問）です。採用した方式は Hit@5 0.72、MRR@5 0.61 です。

| 方式 | Hit@5 | MRR@5 |
|---|---:|---:|
| ベクトル検索だけ | 0.47 | 0.32 |
| キーワード検索だけ | 0.62 | 0.48 |
| 組み合わせただけ | 0.64 | 0.45 |
| 組み合わせ＋並べ直し | 0.72 | 0.61 |

組み合わせただけの MRR@5 がキーワード検索より低いのは、2 つの順位を混ぜると、最初の正解が少し後ろに下がることがあるためです。

評価Bでは、採用した方式の Hit@5 は 0.82、キーワード検索は 0.81 です。差はほとんど出ません。

| 方式 | Hit@5 |
|---|---:|
| ベクトル検索だけ | 0.62 |
| キーワード検索だけ | 0.81 |
| 組み合わせただけ | 0.80 |
| 組み合わせ＋並べ直し | 0.82 |

## 公開デモ

ここからは、リポジトリで再現できる 2,000 件の数字です。同じ故障の言い回しが数通りしかなく、質問もその言葉で書いているので、単語が一致するキーワード検索が高く出ます。採用した方式の Hit@5 も MRR@5 も 0.95 です（表は小数第 3 位まで）。

評価Bは 383 問です。正解が無い質問と、原因分類が「その他」の質問は除いています。自動で付けた正解のうち 30 組を確かめると、27 組が正しい組でした。

### 結果（正解の版 v1.4）

| 方式 | A Hit@5 | A MRR@5 | B Hit@5 | B MRR@5 | 応答時間（A） |
|---|---|---|---|---|---|
| dense | 0.632 | 0.532 | 0.775 | 0.732 | 71 ms |
| sparse | 0.947 | 0.934 | 0.984 | 0.952 | 3 ms |
| hybrid | 0.947 | 0.768 | 0.984 | 0.852 | 78 ms |
| hybrid_rerank | 0.947 | 0.947 | 0.987 | 0.949 | 326 ms |

hybrid_rerank と比べた、質問ごとの勝ち負け（上がった / 同じ / 下がった）

| 比べた相手 | 評価A | 評価B |
|---|---|---|
| dense | 17 / 21 / 0 | 105 / 257 / 21 |
| sparse | 1 / 37 / 0 | 18 / 343 / 22 |
| hybrid | 13 / 25 / 0 | 86 / 279 / 18 |

### 直してきた履歴

直すたびに評価A・B を測りました。まだ判定していない記録が上位 5 件に出たときは、追加で判定して正解の版を上げます（v1 → v1.4）。下の表は、すべて v1.4 で計算し直した値です。

| 直したこと | A dense Hit@5 | A sparse Hit@5 | A hybrid_rerank Hit@5 / MRR@5 | B dense Hit@5 |
|---|---|---|---|---|
| 最初の状態 | 0.579 | 0.921 | 0.947 / 0.947 | 0.616 |
| ベクトル検索の索引を HNSW に | 0.658 | 0.921 | 0.947 / 0.947 | 0.770 |
| 質問にも索引と同じ表記の正規化 | 0.658 | 0.974 | 0.974 / 0.974 | 0.770 |
| 略語の展開を修正 | 0.632 | 0.974 | 0.974 / 0.974 | 0.775 |
| 語を基本形にそろえる（「止まった」と「止まる」を同じ語に） | 0.632 | 0.947 | 0.947 / 0.947 | 0.775 |

最後の変更では評価A が 1 問下がりました（0.974 → 0.947）。直す前に、0.05 未満の差は差がないと決めていたので、活用の違いに強いこの変更を残しています。

結果のファイルは `tools/evaluation/results/<ラベル>.json` です。上の表の最新は `lemma-rescored-v1.4.json` です。

## 限界

- 判定していない記録は不正解として数えています。追加で判定できるのは、上位 5 件に出たものだけです
- 公開デモの評価Bの正解は項目から自動で付けているので、誤りを含みます（確かめた 30 組のうち 3 組）
- AI モードの回答の質は、まだ測れていません
- 上の応答時間は公開デモのものです

## あえてやらなかったこと

| やらなかったこと | 理由 |
|---|---|
| AI の判定をそのまま正解にする | 人の判定と合うかを確かめる手間に見合わないため。下書きにだけ使い、全件を自分で確認しました |
| 統計的な検定 | 質問は現場から無作為に取ったものではないので、検定をしても現場全体の差としては読めません。質問ごとに、最初の正解の順位が上だったかを数えました |
| 段階を付けた正解（nDCG など） | 判定の手間が増える割に、方式の選び方は変わらないため |

## 動かし方

公開デモを測ります。

```bash
docker compose exec rag-api python /app/tools/evaluation/evaluate.py --label <名前> --eval-version v1.4
```

結果は `tools/evaluation/results/<名前>.json` に出ます。上位 5 件にまだ判定していない記録が出たときは、`unjudged_<名前>.csv` に書き出されます。
