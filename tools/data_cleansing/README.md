# データクレンジングパイプライン

本番の保全記録（手書きOCR・オペレータごとの表記揺れ・略語混在）を検索用コーパスに整えるための前処理パイプライン。

## なぜ必要か

RAG の検索精度は**入力データの品質**に直結する。保全記録は以下の問題を抱えることが多い:

| カテゴリ | 具体例 |
|---|---|
| **文字正規化** | 「ＮＣ旋盤」「NC旋盤」「ｎｃ旋盤」が混在 |
| **略語・表記揺れ** | 「圧トラ」「圧力TR」「圧力トランスミッタ」 |
| **OCR エラー** | 手書き記録のスキャン由来（0↔O, 1↔l, 一↔ー） |
| **品質の低いレコード** | 「修理した」「OK」だけ、症状・対処欄が空 |
| **重複** | 同じ故障を複数票に分散記入 |
| **日付形式** | 「2024/1/5」「令和6年1月5日」「R6.1.5」混在 |

## パイプライン構成

```
dirty_sample.csv  ──▶  load
                         │
                         ▼
                   normalize_unicode    (NFKC 正規化、全角半角統一)
                         │
                         ▼
                   normalize_dates      (日付形式統一 → ISO 8601)
                         │
                         ▼
                   canonicalize_equipment (辞書ベース設備名統一)
                         │
                         ▼
                   correct_ocr_errors   (文字混同辞書での補正)
                         │
                         ▼
                   filter_quality       (最小長・エントロピー検査)
                         │
                         ▼
                   deduplicate          (完全一致 + ハッシュ近似重複検出)
                         │
                         ▼
                   cleaned.csv  +  CleansingReport
```

## 実行方法

```bash
# デモ実行（ダミーの汚いデータで動作確認）
python clean_maintenance_logs.py \
  --input dirty_sample.csv \
  --output cleaned_sample.csv \
  --dictionary equipment_dictionary.yaml \
  --report cleansing_report.json
```

## 手法の詳細

### 1. 文字正規化（Unicode NFKC）
全角英数字・カタカナを半角へ統一。`unicodedata.normalize("NFKC", text)`。

### 2. 日付形式統一
`2024/1/5`、`2024-01-05`、`R6.1.5`（和暦）、`令和6年1月5日` 等の複数形式を ISO 8601 (`YYYY-MM-DD`) に統一。和暦は年号辞書でマッピング。

### 3. 設備名の正準化（辞書ベース）
`equipment_dictionary.yaml` で正準名と別名（alias）を管理し、レコード内の文字列を正準名へ置換:

```yaml
- canonical: 圧力トランスミッタ
  aliases: [圧トラ, 圧力TR, 圧力トランスデューサ, PT, 圧セン]
```

本番では**現場の台帳と整合させる**ことが重要。定期的に未登録語のサンプルを抽出して辞書に追加していく運用。

### 4. OCR エラー補正
手書き → スキャン → OCR 経路で頻出する誤認識を補正:

| 誤認識 | 補正先 | 文脈条件 |
|---|---|---|
| `0` (ゼロ) | `O` (オー) | 英字混在時 |
| `l` (エル) | `1` (イチ) | 数字列の中 |
| `一` | `ー` (長音) | カタカナ語直後 |

誤補正を避けるため、**文脈（前後文字）を見て適用**。

### 5. 品質フィルタ
- 症状・対処合計 **20 文字未満** → 除外
- 文字のエントロピー（ユニーク文字数 / 総文字数）が極端に低い → 除外（「あああ」「テストテスト」等）
- `langdetect` で日本語判定 → 他言語混入を除外

### 6. 重複排除
- **完全一致**: `(日付, 設備, 症状, 対処)` のタプルでハッシュ化
- **近似重複**: 本文を MinHash 化し、Jaccard 類似度 > 0.85 を近似重複とみなす（[datasketch](https://github.com/ekzhu/datasketch) を想定）

## 設計上の注意点

1. **すべての除外レコードを `excluded.csv` に保存**し、現場にフィードバックする（記入ルール改善に活用）
2. **辞書は単一の Source of Truth**（YAML） にする。コード内ハードコーディング禁止
3. **冪等性**（同じ入力を 2 回流しても結果が同じ）を保証する
4. パイプライン各段階は**単体テスト可能な形で分離**（本プロジェクトでは `packages/rag-core/tests` 側に配置してもよい）

## 本番との差分

ポートフォリオ版は以下の点を**シンプル化**している:

| 観点 | 本番 | ポートフォリオ |
|---|---|---|
| 辞書サイズ | 約 3,000 語 | 15 語（デモ用） |
| 近似重複 | MinHash + Embedding の 2 段階 | MinHash のみ |
| OCR 辞書 | 50 パターン | 10 パターン |
| 日本語 NLP | fugashi + ipadic-NEologd | MeCab + unidic-lite |

本番では社内のマスタデータと整合する辞書を専任で維持し、四半期ごとに精度評価と辞書更新を行っている。
